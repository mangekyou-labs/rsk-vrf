# BN254 hash-to-curve reference vectors

Ticket: mangekyou-labs/rsk-vrf#14 (feeds #12, Verifier Review Expectation). Researched 2026-10-23. Sources were cloned into empty temp directories and read as text. For the vector work I ran code: Go (drand/kyber, gnark-crypto), a Python port written from RFC 9380, and the pinned `BLS.sol` under Foundry (solc 0.8.24). Live drand beacons were fetched from `api.drand.sh`.

## Answer

Use **gnark-crypto's SVDW map (`bn254.MapToCurve1`) plus a ~25-line RFC 9380 `expand_message_xmd` with Keccak-256**, cross-checked by a **spec-derived Python port**, as the independent reference. Use **drand/kyber** (the real producer of evmnet signatures) as the ground-truth oracle, not as the independent one.

- All four implementations agree bit-for-bit on four evmnet rounds (1, 2, 1000, 10000000): the pinned `BLS.sol` `hashToPoint` (run in Foundry), drand/kyber `Hash`, gnark-crypto `MapToCurve1` with my own Keccak XMD, and the Python port. For the same four rounds the real drand/evmnet beacon signature verifies against the evmnet public key using the kyber hash, so the vectors are the ones drand itself uses, not just the ones Solidity agrees with.
- **drand/kyber is not independent of the Solidity code.** The kyber BN254 hash-to-curve was added by the same author (Kevin Charm, commit `6fadd9d`, 2024-03-18, "Add BN254 (#55)") one day before `bls-bn254` 2.0.0 (`9f70fb4`, 2024-03-19). It is a Go transcription of the same algorithm, so agreement shows consistency, not independent reading of the spec. It is still the right oracle for "what does drand sign".
- **gnark-crypto is independent** of both. It is generated by ConsenSys' generator, has its own SVDW constants and a different structure (constant-time `CMOV` selects, Montgomery `fp.Element`). It cannot do the whole job alone: its `hash.ExpandMsgXmd` is hard-wired to SHA-256, so the XMD step must be supplied. Only the map step, the field reduction and the group addition come from gnark.
- **Danger that the vectors catch:** `BLS.sol` takes the DST as a caller argument. The Solidity repo's own tests and `scripts/hash.ts` use `..._SSWU_RO_NUL_`, but drand evmnet uses `..._SVDW_RO_NUL_`. The comment in `hash.ts` calls the SSWU string "DST used in drand BN254", which is wrong. A wrong DST does not revert, it just yields different points. Pin the DST string in tests.
- Recommended bar for #12: commit the four (or more) vectors below with the DST and message construction, run them against our vendored `BLS.hashToPoint`, and also run the gnark/Python generator in CI or as a one-off script. The `expand_message` output and `u0`/`u1` are included so a failure can be localised to XMD, field reduction or the map.

## What evmnet actually specifies

- Scheme ID `bls-bn254-unchained-on-g1`, signatures on G1, keys on G2. Source: `drand/drand` `crypto/schemes.go` lines 253-293 at `e8dd607147c676086312b21c22d923dd6a07209a` (2026-10-07).
- DST (G1): `BLS_SIG_BN254G1_XMD:KECCAK-256_SVDW_RO_NUL_` (43 bytes), set via `Pairing.SetDomainG1(...)` at `crypto/schemes.go:264`. The G2 DST at line 265 is the same with `G2`.
- Signed message ("unchained"): `keccak256(uint64_be(round))`, from `DigestFunc` at `crypto/schemes.go:273-278` (`sha3.NewLegacyKeccak256`, `binary.Write(..., BigEndian, round)`). `GetRound()` is a uint64, so 8 bytes.

The Solidity constants were independently re-derived: the Python port finds `Z` with the RFC 9380 App. H.1 `find_z_svdw` procedure and gets `Z = 1`, `c1 = 4`, `c2 = 0x1832...7ea3`, `c3 = 0x16789af3...fffffa` (with `sgn0(c3) = 0`), `c4 = 0x10216f7b...a9bd`, all equal to `BLS.sol` lines 35-49. ## How to regenerate

1. **Python (no dependencies besides Python 3).** The script below includes a pure-Python Keccak-256 (asserts the empty-input digest `c5d2460186f7...a470`), `expand_message_xmd`, `hash_to_field`, `find_z_svdw`, the SVDW map and affine addition. Run `python3 -I ref.py`; it prints constants and the four vectors.
2. **Go harness (drand/kyber + gnark-crypto).** A small `main.go` in its own module that: builds `kbn.NewSuite()` from `github.com/drand/kyber/pairing/bn254`, calls `SetDomainG1([]byte(dst))`, and gets `suite.G1().Point().(kyber.HashablePoint).Hash(msg)`; separately computes the Keccak XMD (`golang.org/x/crypto/sha3.NewLegacyKeccak256`, 136-byte zero pad), reduces each 48-byte block with `fp.Element.SetBigInt`, calls `bn254.MapToCurve1` twice and adds the results with `G1Jac.AddAssign`; then fetches `/v2/beacons/evmnet/rounds/<n>`, unmarshals the signature and the evmnet public key, and checks `suite.Pair(sig, G2.Base()) == suite.Pair(H, pk)`. kyber `go.mod` requires Go 1.26.8, so Go will auto-download that toolchain. I used `replace` directives pointing at local clones of kyber and gnark-crypto at the commits above. I did not commit the harness, since the issue asked for a research note only. The XMD and field-reduction code in it is the same logic as in the Python block.
3. **Solidity.** Copy `contracts/BLS.sol` and `contracts/ModExp.sol` from `kevincharm/bls-bn254@9f70fb4dff2cd0921dc2144929dc0aff6f21a9b9` into a Foundry project (`solc = "0.8.24"`, `evm_version = "cancun"`; the precompiles 0x05 and 0x06 are standard), deploy a thin wrapper that returns `BLS.hashToPoint(dst, abi.encodePacked(keccak256(abi.encodePacked(uint64(round)))))`, and compare. The wrapper is needed because `hashToPoint` is `internal`.

# Independent spec-derived reference: RFC 9380 expand_message_xmd (H=Keccak-256, legacy padding),
# hash_to_field (L=48, m=1, count=2), generic SVDW (6.6.1, Z per Appendix H.1), BN254 G1 (y^2=x^3+3, cofactor 1).
import sys
p=21888242871839275222246405745257275088696311157297823662689037894645226208583
A,B=0,3
M64=(1<<64)-1
RC=[0x0000000000000001,0x0000000000008082,0x800000000000808A,0x8000000080008000,0x000000000000808B,0x0000000080000001,0x8000000080008081,0x8000000000008009,0x000000000000008A,0x0000000000000088,0x0000000080008009,0x000000008000000A,0x000000008000808B,0x800000000000008B,0x8000000000008089,0x8000000000008003,0x8000000000008002,0x8000000000000080,0x000000000000800A,0x800000008000000A,0x8000000080008081,0x8000000000008080,0x0000000080000001,0x8000000080008008]
ROT=[[0,36,3,41,18],[1,44,10,45,2],[62,6,43,15,61],[28,55,25,21,56],[27,20,39,8,14]]
def rol(x,n):
    n%=64
    return ((x<<n)|(x>>(64-n)))&M64 if n else x
def f(s):
    for rc in RC:
        C=[s[x][0]^s[x][1]^s[x][2]^s[x][3]^s[x][4] for x in range(5)]
        D=[C[(x-1)%5]^rol(C[(x+1)%5],1) for x in range(5)]
        s=[[s[x][y]^D[x] for y in range(5)] for x in range(5)]
        Bm=[[0]*5 for _ in range(5)]
        for x in range(5):
            for y in range(5):
                Bm[y][(2*x+3*y)%5]=rol(s[x][y],ROT[x][y])
        s=[[Bm[x][y]^((~Bm[(x+1)%5][y])&Bm[(x+2)%5][y]) for y in range(5)] for x in range(5)]
        s[0][0]^=rc
    return s
def keccak256(m:bytes)->bytes:
    rate=136; m=bytearray(m); m.append(0x01)
    while len(m)%rate: m.append(0)
    m[-1]|=0x80
    s=[[0]*5 for _ in range(5)]
    for off in range(0,len(m),rate):
        blk=m[off:off+rate]
        for i in range(rate//8):
            s[i%5][i//5]^=int.from_bytes(blk[8*i:8*i+8],'little')
        s=f(s)
    out=b''
    for i in range(4): out+=s[i%5][i//5].to_bytes(8,'little')
    return out
assert keccak256(b'').hex()=='c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470'
def xmd(msg,dst,n):
    b_in=32; ell=-(-n//b_in); dp=dst+bytes([len(dst)])
    z=bytes(136)
    b0=keccak256(z+msg+n.to_bytes(2,'big')+b'\x00'+dp)
    bs=[keccak256(b0+b'\x01'+dp)]
    for i in range(2,ell+1):
        bs.append(keccak256(bytes(a^b for a,b in zip(b0,bs[-1]))+bytes([i])+dp))
    return b''.join(bs)[:n]
def h2f(msg,dst,count=2):
    L=48; u=xmd(msg,dst,count*L)
    return [int.from_bytes(u[i*L:(i+1)*L],'big')%p for i in range(count)]
inv0=lambda x: pow(x,p-2,p)
def is_sq(x): return pow(x,(p-1)//2,p) in (0,1)
def sqrt(x):
    assert p%4==3
    r=pow(x,(p+1)//4,p); assert r*r%p==x
    return r
sgn0=lambda x:x%2
g=lambda x:(x**3+A*x+B)%p
def find_z():
    # RFC 9380 App. H.1 find_z_svdw
    ctr=1
    while True:
        for Z in (ctr,p-ctr):
            gz=g(Z)
            if gz==0: continue
            h=(-(3*Z*Z+4*A)*inv0(4*gz))%p
            if h==0 or not is_sq(h): continue
            if is_sq(gz) or is_sq(g((-Z*inv0(2))%p)): return Z
        ctr+=1
Z=find_z()
c1=g(Z); c2=(-Z*inv0(2))%p
c3=sqrt((-c1*(3*Z*Z+4*A))%p)
if sgn0(c3)==1: c3=p-c3
c4=(-4*c1*inv0(3*Z*Z+4*A))%p
def svdw(u):
    tv1=u*u%p*c1%p; tv2=(1+tv1)%p; tv1=(1-tv1)%p; tv3=inv0(tv1*tv2%p)
    tv4=u*tv1%p*tv3%p*c3%p
    x1=(c2-tv4)%p; x2=(c2+tv4)%p
    x3=((tv2*tv2%p*tv3%p)**2%p*c4+Z)%p
    for x in (x1,x2,x3):
        if is_sq(g(x)): break
    y=sqrt(g(x))
    if sgn0(u)!=sgn0(y): y=p-y
    return x,y
def add(P,Q):
    if P is None: return Q
    if Q is None: return P
    (x1,y1),(x2,y2)=P,Q
    if x1==x2:
        if (y1+y2)%p==0: return None
        l=3*x1*x1*inv0(2*y1)%p
    else: l=(y2-y1)*inv0(x2-x1)%p
    x3=(l*l-x1-x2)%p
    return x3,(l*(x1-x3)-y1)%p
def hash_to_g1(msg,dst):
    u0,u1=h2f(msg,dst)
    return add(svdw(u0),svdw(u1)),(u0,u1)
if __name__=="__main__":
    print("Z",Z,"c1",hex(c1),"c2",hex(c2),"c3",hex(c3),"c4",hex(c4))

        P,u=hash_to_g1(msg,dst)
        print("round",r,"msg",msg.hex(),"u0",u[0],"u1",u[1],"x",P[0],"y",P[1])

## Caveats and what I did not verify

- The Go harness and `ref.py` live outside the repo (temp directory); only `ref.py` is reproduced above. The Go harness is described, not committed.
- "Independent" is relative: gnark-crypto and the Python port are independent of `BLS.sol` and kyber, but the Keccak-XMD and the 48-byte reduction in my Go and Python code are my own reading of RFC 9380 and share my assumptions. Their agreement with the production drand signer on live beacons is what rules out a shared misreading.
- Only four rounds were tested. I did not instrument which SVDW branch (x1, x2, x3) each sample took; edge cases of SVDW (u with `tv1 = 0`, `x3` branch, u = 0, `g(x) = 0`) are not covered. `mapToPoint` test vectors from `test/vectors/svdw.ts` (Sage-generated) were not re-run through gnark.
- Solidity was run under Foundry with solc 0.8.24 / cancun (not the repo's hardhat config); `ModExp.sol` was used unmodified.
- Only G1 (the evmnet signature group) was checked. G2 hash and pairing check in Solidity (`verifySingle`) were not exercised.
- The statement that the Sage reference was the origin of `test/vectors/svdw.ts` rests on its one-line header comment; I did not locate the Sage script.
- RFC 9380 text was not re-fetched; section numbers are from memory of the RFC and the code comments (the code in kyber and gnark links to 5.3.1 and 6.6.1 / straightline-svdw).
- Audit status: none of the compared implementations is audited for this specific use; `randa-mu/bls-solidity` self-labels as unaudited.
